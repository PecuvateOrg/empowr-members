## 2026-08-18 (session 5) — UX pass: no loading boundaries existed anywhere; also shipped and fixed a prerender regression on /sessions (PRs #4, #5, #6 all MERGED and live)

User asked whether framer-motion and a third-party UI/UX skill were the answer to remaining UX roughness. Neither was the first problem.

- **The app had no `loading.tsx` or `error.tsx` anywhere.** On the App Router that means a server navigation shows the *old* page until the new one is ready — a tap looks like nothing happened — and Next cannot prefetch a dynamic route past a boundary that does not exist. Added boundaries for `(member)`, `(admin)`, `/ticket/[id]` and `/sessions/[slug]` with a shared `PageSkeleton` sized to each page's real container. Plain `animate-pulse`, deliberately not a motion library: it must render before any JS has.
- **`/sessions` filtering moved to the client**, so a chip tap does **0 document requests** instead of a full server navigation, and the route went `f (Dynamic)` -> `o (Static)`. Session 3 had called 274ms this route's hard floor *because* it read `searchParams`; that constraint is gone.
- **The filter rule now lives once**, in the new client-safe `lib/catalogue-filters.ts`, imported by both `lib/catalogue.ts` and the client UI.
- **Latent bundle bug fixed**: `OfferingCard` took a *value* import (`TYPE_LABELS_SINGULAR`) from `lib/catalogue`, which carries `import "server-only"`. Harmless while only server components rendered it; would have broken the bundle the moment the client filter UI did.
- **Consent banner was covering the primary CTA on every page** until dismissed. Now compact (250px -> 121px at 375px) with a spacer of its own **measured** height so the page always scrolls clear. Copy kept at `text-sm`: a legal notice should not be the smallest type on the page.
- **Built a `useLinkStatus` spinner for the Book links, then REMOVED it.** With a loading boundary present Next commits to the skeleton immediately, so `pending` never became true across 40 samples at 50ms.
- **[REGRESSION] Shipped a regression in PR #5, caught verifying the production deploy, fixed in PR #6.** `/sessions` served its **Suspense fallback as the page's static HTML** — `animate-pulse` chips as rendered DOM, offerings only in the serialized RSC payload. Cause: `useSearchParams()` during render is a dynamic API, so Next skipped prerendering the subtree. Cold loads flashed a skeleton and crawlers saw no sessions on the main public catalogue page. **The route reported `o (Static)` throughout** — the build legend gives the render *mode*, never what is inside the output. Fix: seed filters unfiltered and read `window.location.search` in a mount effect. Saved as `[[feedback_static_route_can_prerender_skeleton]]`.
- **On the original question**: framer-motion still has not earned its import — it costs users zero bytes only while nothing imports it, and motion would have decorated the dead air rather than closed it. The third-party `ui-ux-pro-max` skill was assessed and declined: it is a greenfield design-system *generator*, and this app already has an authoritative system in `brand-identity.md` shared across 8 Empowr sites.

## 2026-08-18 (session 3) — Public catalogue was uncacheable by design, not slow at the database; fixed and measured (PR #3, open NOT merged)

User reported the platform felt unoptimised with poor latency. Measured production first: `/sessions` 1.0-4.4s TTFB, `/sessions/skate-jam` ~0.59s p50. **The database was never the bottleneck** — every hot path is indexed, Supabase's performance advisor flags nothing on `mem_` tables, and the whole dataset is 4 offerings / 51 occurrences / 3 bookings. The cause was `force-dynamic` on the catalogue making it uncacheable (`Cache-Control: private,no-cache,no-store`, `Netlify Durable: fwd=bypass`), so every visit paid a function invocation plus a transatlantic round trip on top of the `us-east-2`/`eu-west-2` split logged in session 2.

- **Catalogue now served from cache.** New `lib/supabase/public.ts` (cookie-free anon client) — `lib/supabase/server.ts` reads `cookies()`, a dynamic API, so anything touching it can never be cached; the catalogue tables carry identical anon/authenticated RLS policies so dropping the cookie changes no rows. All catalogue reads wrapped in `unstable_cache()` under one `catalogue` tag; cached queries apply no time filter (callers drop past occurrences in memory) so an entry stays correct however old it is. New `lib/revalidate.ts`; all 12 catalogue-affecting admin write handlers call `revalidateCatalogue()` (check-in excluded — booking status only).
- **🔴 `export const revalidate` alone was inert.** Swapping `force-dynamic` → `revalidate = 300` on `/sessions/[slug]` typechecked and built fine but the route stayed `ƒ (Dynamic)`. Without `generateStaticParams()` Next has no slug list and cannot prerender a dynamic segment; nothing errors or warns. Adding it (fail-open, returns `[]` on error) flipped it to `● (SSG)`. **Read the build legend, never infer caching from source.** Saved as `[[feedback_next_revalidate_needs_static_params]]`.
- **Auth round trips cut**: middleware now returns early on routes needing no session instead of building a client and calling `getUser()` (a real network call whenever a session cookie is present) to discard the answer; `getAuthedAccount()` wrapped in React `cache()`; both booking pages resolve account + occurrence concurrently.
- **Measured on the deploy preview** (12 samples, reused connection): `/sessions/[slug]` **586ms → 30ms p50**, now `Netlify Edge; hit`. `/sessions` 344ms → 274ms — **that is its ceiling**: it reads `searchParams` so it still renders per request, and the ~70ms saved is exactly the one Supabase round trip removed. Going further means moving the type/age filters client-side so the route can go static (UX change, not done).
- **`getClaims()` considered and DECLINED by the user.** This project uses ES256 keys so supabase-js could verify JWTs locally and drop the last auth round trip — but `jwt_exp=3600`, so a remotely revoked session would stay accepted on server-rendered pages for up to an hour. Wrong trade for a platform taking real payments. Do not re-propose without raising the revocation window first.
- **E2E-verified the invalidation, with a control.** Created an orphan venue (attached to nothing, so publicly invisible) through the real deployed admin API and watched `/sessions/skate-jam`: control window 0 re-renders over 40s, treatment `age` reset to 2 with `"Next.js"; fwd=miss` immediately after. **The purge is asynchronous, ~5s** — an earlier sample at 0-3s still showed `hit` and looked like a failure. `ttl` is NOT a usable signal (absent on a miss); use `fwd=miss` + an `age` reset. Cleanup confirmed against the DB: `mem_venues` back to 4, zero probe rows, offerings untouched.
- **Corrected a claim I made earlier the same session**: the chained `.or()` age filter in `listOfferings` was **not** buggy — PostgREST ANDs repeated `or=` params, verified directly against the REST endpoint. The in-memory filter reproduces the same truth table; it moved for cacheability, not correctness. The false claim had been written into a code comment and was removed.
- **`framer-motion` investigated, deliberately KEPT.** Zero imports, nothing depends on it, 9.7MB of `node_modules` — but since nothing imports it, it never enters the module graph and costs users zero bytes. Removing it is dependency hygiene, not performance. User chose to keep it for possible future use. (Same unused dep also sits in `PecuvateCommons/black-biz-ref` — untouched.)
- **Qualifies session 2's "three mobile issues, all fixed"**: the user reports the platform still does not feel responsive on mobile and small screens. Session 2's fixes were real but evidently not sufficient — a proper multi-viewport audit is still outstanding, not a re-run of the 375px overflow check that already missed the header-wrap issue once.
- **Next session**: (1) responsive/mobile audit + a functional pass, (2) amend Programme Policies + T&Cs to v1.2 then build member self-serve cancellation/transfer/reschedule — see the workspace DEVLOG for the blast radius. ## 2026-08-17 (later session) — PassKit removed, replaced with an in-house QR ticket page

The team reviewed a mockup for an in-house alternative to wallet passes and decided to switch: PassKit had been a recurring source of project-specific pain (a hand-rolled JWT sat silently on its 60s rejection boundary for weeks; production stuck in `PROJECT_DRAFT` mode, stamping every pass "Test Pass" and expiring it after 48h — the real launch blocker, after an earlier theory wrongly blamed a missing Apple Developer cert; Google Wallet only worked through a third-party reader). None of that complexity served the actual requirement — "staff can verify a booking at the door" — which a QR code resolving to a live status lookup does exactly as well, for zero vendor dependency and zero per-pass cost. `PASSKIT_ENABLED` had been off in production throughout, so removal carried no live-pass regression risk.

- **New public ticket page** (`/ticket/[bookingId]`) — deliberately **unauthenticated**, a deliberate product decision confirmed with the user: a grandparent or other adult collecting/dropping off a child can pull the ticket up on their own phone without the member's login. Trust model is the same this app already gives Stripe's `checkout_session_id` on `/book/confirmation` — the booking id is a high-entropy UUID, not sequential. `lib/ticket.ts`'s `getTicket()` is a deliberately separate selector from the admin check-in query, hard-scoped to ticket-safe fields only (offering, when, venue, participant first name, price, status) — never email, DOB, medical notes, or Stripe ids. Always reads live status (`force-dynamic`), so a cancelled booking just renders a "no longer valid" state automatically — no revocation mechanism needed, unlike PassKit's `voidPass()`.
- **QR encodes a URL**, not a bare ref — `/admin/checkin/[bookingId]`, scanned with the phone's native camera app. `netlify.toml` already ships `Permissions-Policy: camera=()` site-wide, so an in-page scanner wasn't the right fit here anyway.
- **New admin check-in flow**: `/admin/checkin/[bookingId]` inherits the existing `(admin)` group's session + `ADMIN_EMAILS` allowlist gate — no new kiosk/PIN auth system, since this is a device logged in once before doors open, not a walk-up public kiosk. Deliberately a **read-only lookup**, not an auto-mark-on-scan: a GET must never mutate (bots/link-previews/back-button reloads would silently check people in), and staff need the visual-confirm step for safeguarding anyway. `POST /api/admin/bookings/[id]/checkin` does the actual flip, guarded by an optimistic status claim so a second scan just no-ops into "Already checked in."
- **`per_run` (course) bookings are a known, deliberately-surfaced gap**: the schema has no per-week attendance concept, so marking one week attended would make the whole run look done for every other week. The check-in page hides "Mark attended" for course-run bookings (both client-side and re-checked server-side in the API route) rather than silently corrupting status semantics.
- **No DB migration.** The ticket "token" is the existing `mem_bookings.id`; `attended`/`no_show` already existed in `BookingStatus` unused; `mem_bookings.updated_at` is already trigger-maintained, giving a check-in timestamp for free. `mem_bookings.passkit_pass_id` / `mem_venues.passkit_venue_id` are left as harmless dead columns — dropping them is a separate future migration, not bundled into this app-level change.
- **Confirmation email**: the wallet-install `ctaButton()` is now "View your ticket" (or "View {name}'s ticket" for multi-child bookings), pointing at `membersUrl('/ticket/'+id)` — computed synchronously in `notifications.ts`, no async issuance round-trip like PassKit needed. `BookingEmailSummary.passInstallUrls: (string|null)[]` → `ticketUrls: string[]`, always populated now.
- **`lib/passkit.ts` deleted entirely**; call sites stripped from the Stripe webhook, `POST /api/admin/venues`, and the occurrence-cancel route. `PASSKIT_API_KEY`/`PASSKIT_API_SECRET` removed from `.env.example`. `planning/passkit/CONTEXT.md` left in place as historical record, matching this repo's convention — Netlify/vault env var cleanup is a non-blocking follow-up, not done this session.
- Small refactor along the way: extracted `courseRunWhen()` (was private to `notifications.ts`) into `lib/format.ts` so `lib/ticket.ts` could reuse it instead of duplicating the fold logic; same for a new shared `lib/booking-status-labels.ts` (was a private `STATUS_LABELS` map duplicated between the admin register page and the new check-in page).
- **E2E-verified against the real database and a real (self-signed) Stripe webhook event**, not reimplemented: booked the `localdev.test@empowrcic.org` test account's minor participant onto a temporarily-reactivated offering through the real UI up to the real Stripe Checkout redirect, then self-signed a `checkout.session.completed` event (`stripe.webhooks.generateTestHeaderString`, same pattern as the 2026-07-21 PassKit e2e proof) and POSTed it to the local webhook — confirmed the booking flipped to `confirmed` in the DB. Loaded `/ticket/[id]` in a **fresh, cookie-less browser context** (proving the no-login claim, not just asserting it) and confirmed the ticket rendered correctly with a real QR image. Logged in as admin, opened `/admin/checkin/[id]`, hit "Mark attended," confirmed the status flipped to `attended`, the button became "Already checked in" idempotently on reload, and the ticket page still rendered correctly afterward showing a "Checked in" state. Separately confirmed an old cancelled test booking's ticket page renders "This booking is no longer valid" rather than a ticket. Cleaned up: offering flipped back to `inactive` after testing; left the confirmed/attended test booking in place (harmless test data on the user's own test account, same account used for tier-1 waiver testing).
