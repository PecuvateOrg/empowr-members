## 2026-08-17 — Tier 1 built (scoped down after a Waivers-side retention change), plus per-booking departure consent; PR #1 unblocked

Picked back up from the 2026-08-10 pause. Before building, found that Waivers had independently shipped `20260813140645_waiver_retention_three_year_window` on 2026-08-13/14 — `waiver_responses`/`departure_consents` now persist 3 years from `session_date` (evidence-retention purpose, unrelated to Members) instead of purging next-day. Since `checkWaivers()` never filtered by `session_date` in the first place, this alone made "sign once" functionally true again without any of tier 1 being built — the original urgency was gone. Decision (with the user): build a **smaller** tier 1 anyway, not for retention, but because the booking gate was implicitly hostage to a table and policy Members doesn't own — Waivers could change it again for their own legal reasons and silently break booking here a second time, and the `form_versions.active` landmine (any wording fix instantly un-covers everyone) was still live regardless of retention.

- **`mem_waiver_consents` built** — migration `20260817152231` on the shared `empowr-cic` project (applied via the Management API, no CLI/MCP path available; registered into `supabase_migrations.schema_migrations` by hand since the raw-SQL endpoint doesn't write the ledger itself — see the gotcha below). One row per `mem_participants.id`, partial unique index enforces at most one active (`revoked_at IS NULL`) row per participant, `waiver_response_id` kept for audit lineage only. Gate is exactly the original design: `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())` — never joins `form_versions` or `waiver_responses` again.
- **Tier 2 (session-dated write at booking) dropped from scope** — the 3-year retention window already does that job; building a second write path wasn't worth it.
- **`checkWaivers()` rewritten as two-tier**: `mem_waiver_consents` is checked first (fast, decoupled); anyone without a row falls back to the original email/name match against `waiver_responses` — this is what still recognises someone who signed on the standalone `waiver.empowrcic.org` app before ever touching Members. A fallback match now also lazily backfills a consent row (same "persist fresh matches" pattern the booking route already used for `person_id`), so it only ever runs once per participant. `submitWaiver()` writes its own consent row directly at sign time.
- **Per-booking departure consent built**, replacing the one-time `consent_unaccompanied_departure` flag `submitWaiver()` used to write (now always `null` from Members — superseded). New `mem_participants.default_travel_method` column (migration `20260817152232`) pre-fills the toggle from the participant's profile; the toggle itself defaults on when a default exists, but the 5 `confirm_*` affirmations always start unchecked and must be re-given fresh every booking, per the 2026-08-10 decision that this judgement can reasonably change session to session. Writes into Waivers' own `departure_consents` table (`session_date` = the occurrence's date), same "write into the tables the standalone app owns" pattern as the waiver itself, so `staff_today_departure_consents()` keeps working unchanged.
- **PR #1's "only need to do this once" copy is no longer false** — left unchanged on `/waiver`, since it's now actually true (consent persists until revoked, not until the next form-version bump or Waivers retention change).
- **🔴 PowerShell gotcha, cost real time**: `Get-Content -Raw` on this machine returns a value that isn't a plain string — piping it into `@{query=$sql} | ConvertTo-Json` produced a 3.8MB payload from a 1870-byte file (pipeline metadata serialized alongside the content) and the Management API 413'd. ## 2026-08-10 — Retention blocker cleared at the database: the purge now keys on session_date, and a latent FK would have killed the job entirely

The blocker recorded below is fixed. Migration `20260810114838_waiver_retention_by_session_date` is applied to the shared `empowr-cic` project and committed to **`empowr-cic-workspace`** (`Empowr CIC/supabase/migrations/`) — not here, per the 2026-08-06 schema-of-record split.

- **User resolved the governance question that was blocking the fix.** The 2026-08-09 entry recorded the `session_date` change as "needs the Waivers owner to agree". There is no separate owner — Waivers and Members are one Empowr CIC system, and the only real constraint is not disturbing door/walk-in behaviour. Verified that constraint holds rather than assuming it: walk-ins sign same-day or the night before, so their `session_date` is the same calendar day and they purge on exactly the same night as before. The rules only diverge at 2+ days ahead, where the *old* rule deleted the record before the session — so the change is a strict improvement for walk-ins, never a regression.
- **🔴 Found a latent landmine that would have silently killed retention altogether.** `mem_participants.person_id` was `ON DELETE NO ACTION` (the other two FKs into `people` are CASCADE; this one was not). The job ends with a mass `DELETE FROM people`, so the moment Members stamps a participant with a `person_id` — which is exactly what PR #1 does — that DELETE raises an FK violation. pg_cron runs the job as a single implicit transaction, so the violation rolls the *whole* job back and **nothing is ever purged again**, visible only in `cron.job_run_details`. Fixing an over-aggressive retention rule would have produced indefinite retention of everything instead. Flipped to `SET NULL`. It had not fired yet only because `mem_participants` has 0 rows with `person_id` set. Note the earlier design notes cite this FK as a *convenience* ("FK already present, no migration needed") — its delete rule was never checked.
- **Departure consents now get the window they were always meant to have.** The 2026-08-09 Waivers DEVLOG recorded them as being destroyed *early* ("~14 hours old, well inside the intended 24") via CASCADE off the `people` cleanup. They have their own `session_date` column (added 08-05), so the fix is symmetric with waivers rather than a new retention policy — which is what that entry implied and what a mid-session detour toward "12 months vs indefinite" had drifted away from.
- **Two robustness additions**: `NOT IN` → `NOT EXISTS` (a NULL `person_id` would make the entire cleanup a silent no-op), and a 13-month `submitted_at` backstop so a mistyped far-future `session_date` cannot retain a record forever — `session_date` is app-supplied, so the old rule's guaranteed time ceiling would otherwise have been lost.
- **Verified, not assumed**: single cron job after reschedule (no duplicate), `confdeltype = 'n'`, and a read-only date matrix across seven walk-in/member/typo scenarios. Live data: 0 rows would be deleted at the next run.
- **Design decision recorded — departure consent is per-booking, not standing.** A standing risk waiver and a standing "my child may leave alone" consent are not equivalent in risk: the latter is a judgement a parent may make differently on a dark December evening than a July one, and it carries a specific `travel_method`. So the waiver becomes standing (tier 1) with a derived per-session row, while **departure consent is asked at each booking**, pre-filled from an updatable default in the member profile. Friction stays low without removing the per-occasion judgement.
- **Tier 1 was designed but deliberately NOT built.** `mem_waiver_consents` is specced — one row per participant (so adding a child tops up rather than forcing a full re-sign), and critically the gate checks `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())` rather than "consent against the *active* form version". That sidesteps the `form_versions.active` landmine: a typo fix would otherwise un-cover every member simultaneously. `form_version_id` is still recorded for audit, and nullable `expires_at` means the annual-consent decision becomes a code change, not a migration.
- **Build paused at the user's call for an architecture review first** — the shared-database structure needed mapping before more tables were added to it. Outcome in `_config/guides/supabase-structure-blueprint.md`. **Conclusion: nothing blocks this build.** `mem_waiver_consents` is `mem_`-prefixed (app-private), touches no cron job and no `auth.users` trigger, and its only cross-app edge is to `form_versions` — append-only reference data with no purge job. The review did change the build: explicit `GRANT`s are required or every PostgREST call fails `42501` on this project.
- **Still open before PR #1 can merge**: tier 1 (standing consent table), tier 2 (session-dated write at booking), per-booking departure consent with a profile default, repointing `checkWaivers()` to read standing consent rather than `waiver_responses`, and PR #1's "only need to do this once" copy — still false until tier 1 lands.

## 2026-08-09 — Waiver copy aligned verbatim; 24h retention found, which invalidates Phase 1's core premise — PR #1 now ON HOLD

- **Aligned the in-app waiver copy verbatim with the standalone form** at user request: all three agreement cards now carry the canonical title/description/toggle wording from `Empowr-Waivers/StepAgreements.tsx`, the relationship field became a select with the canonical eight options, and `photographyConsent` was added to `links.ts` (the third consent doc had no link at all).
- **Photo consent is now REQUIRED**, matching the standalone form. It was optional in my first cut. Verified live: 400 with the canonical message when unticked, 201 with all three ticked. Flagged separately that mandatory photo consent is a questionable "freely given" basis under UK GDPR — inherited deliberately, not by oversight.
- **Removed the emergency-contact backfill onto `mem_participants`.** The standalone form states "Required each time they attend — contact numbers are not stored on file"; copying waiver-collected contacts into participant records contradicts that notice. Verified afterwards that participant rows keep `emergency_contact_name = null`.
- **Found `delete-old-waivers` (pg_cron, daily 03:00): `waiver_responses` are deleted after 24 hours.** This **invalidates the core premise of the 2026-08-06 entry below** — its "sign once for each person" is false, and the `/waiver` page says so in copy. A member signs today, the row is purged at 03:00, and `checkWaivers()` blocks them again tomorrow. Phase 1 cannot work as designed.
- **Second defect, in Phase 1 itself**: the staff check-in portal queries `waiver_responses` filtered `session_date = today`, but the in-app waiver writes `session_date` = the *signing* date. A member signing today and attending next week would not appear at check-in.
- **Data-loss scare investigated and cleared.** `people`/`waiver_responses`/`departure_consents` went 5/1/4 to 0/0/0; I treated myself as prime suspect, having run repeated deletes against `people` (both consent tables CASCADE off it). Cause was the nightly purge running 08-07 (`DELETE 4`) and 08-08 (`DELETE 1`) while the session sat idle across days — confirmed in `cron.job_run_details`. Nothing I ran touched real rows.
- **Design agreed with user (not built)**: two tiers — account-level standing consent in a new `mem_` table immune to the purge, plus a session-specific step at booking writing a properly-dated `waiver_responses` row so staff check-in keeps working. **Blocker first**: the purge keys on `submitted_at`, not `session_date`, so a row written at booking time dies before the session. Preferred fix is changing the purge to `session_date < current_date` — needs the Waivers owner.
- **PR #1 is ON HOLD**, not merged — it promises persistence the database removes overnight.
